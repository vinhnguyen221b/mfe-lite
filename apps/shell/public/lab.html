1 · Overview

Two ways to split one website.

MFE Lite is two Next.js apps, a shell and a blog, deployed as two Vercel projects behind one domain, mfe-lite-shell.vercel.app. They share the site in two ways: by URL (vertical) and inside a page (horizontal). Switch between them below.

Shell · the default app

Vercel project mfe-lite-shell, folder apps/shell. Owns /, /horizontal and every path nobody else claims, including its 404 page. Holds the routing table.

Blog · the child app

Vercel project mfe-lite-blog, folder apps/blog. Owns /blog, /docs and /components, plus everything under them. Builds and deploys on its own.

Group · one domain

The Vercel microfrontends group mfe-lite puts both projects behind the shell's domain. Visitors only ever see mfe-lite-shell.vercel.app.

2 · Vertical · split by URL

Every URL belongs to exactly one app.

Vercel reads one routing table and sends each request to the project that owns its path, before any app code runs. Neither app ever forwards a request to the other.

Styles stay apart

Each card arrives inside <template shadowrootmode="open"> with the blog's own stylesheet. The shell's CSS does not reach in, the blog's does not leak out, and document.querySelector on the page does not see the card.

One React

remote-components shares react, react-dom and next/*, so the blog's button runs inside the shell's React tree. Every other package, workspace ones included, is bundled once per app, unless both apps list it as shared (see C).

Same road as a visitor

The src is relative. On Vercel it resolves against the production domain, so the shell's server asks mfe-lite-shell.vercel.app/components/… and the routing table sends it to the blog.

COne Like, two apps

The Like button is the blog's code; the ♥ in the header and the provider that holds the count are the shell's. Each app bundles its own packages, so by default each would have its own React context. Both apps list one module as shared, so on this page they use one. Press Like, then turn shared off.

One page at a time

A context lives as long as the page. A reload or a move to the other app starts a new React tree, and that app's layout provider loads the count saved in this browser. A count shared by every visitor would need a server.

In the browser only

Every provider renders 0 into the HTML and loads the saved count after hydration. The blog renders the card's HTML under its own layout; the shell's module takes over once the page runs.

The module is an API

The blog's button runs against the shell's build of likes-context. Change count, like and owner so both the old and the new side keep working.

!Rules that are easy to miss

  1. List the bare path and the wildcard. ["/blog", "/blog/:path*"]. Patterns match whole segments: /blogroll is not /blog/…, so it stays with the shell.
  2. The default app lists no paths. It gets every path nobody claims, its own 404 included. Only children have a routing block.
  3. Redeploy both projects once after creating the group. Deployments built before the group existed ignore microfrontends.json. Hobby allows one group of two projects.
  4. Keep the shell's proxy off the blog's URLs. Its matcher skips _next/, vc-ap-, /blog, /docs and /components, so it only runs for the shell's own pages.
  5. Expose from a path the blog owns. A component lives at /components/<name>, and the routing table gives /components to the blog, so a relative src reaches it through the normal routing.
  6. Render the host per request and guard every slot. force-dynamic keeps the shell's build independent of the blog; an error boundary and Suspense around each slot keep a failing card from taking the page down.
  7. List a context module as shared on both sides. Only react, react-dom and next/* are shared by default; anything else exists once per app, so a context there would split. Across full page loads nothing is shared at runtime: save what must survive.

$Try it yourself

Every response carries x-mfe-zone, stamped by the app that answered. Run these against the live site, or locally.

Against the live site

H=https://mfe-lite-shell.vercel.app
curl -sI $H/                      | grep x-mfe-zone   # shell
curl -sI $H/blog/hello-world      | grep x-mfe-zone   # blog
curl -sI $H/blogroll              | grep x-mfe-zone   # shell (404)
curl -sI $H/components/reactions  | grep x-mfe-zone   # blog

# /horizontal arrives with both blog cards in its HTML
curl -s $H/horizontal | grep -o 'data-remote="[a-z-]*"'

On your machine

pnpm install
pnpm dev     # shell :3000, blog :3001, proxy :3024
open http://localhost:3024/horizontal

pnpm test    # routing table, proxy matcher, shared likes

The local proxy on 3024 reads microfrontends.json and does what Vercel's routing does in production. Open the site through it, not through 3000 or 3001.
